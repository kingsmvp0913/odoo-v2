## 3. 我寫規格時自己做的設計選擇（討論時沒有逐一問過，請特別看）

| # | 選擇 | 理由 | 在哪 |
|---|---|---|---|
| D1 | 客戶管理員存成**新的 role 值 `company_admin`**，不重用 `admin` | 程式裡至少 6 處自己判斷 `role === 'admin'`；重用的話漏改一處，客戶管理員就在那裡變成平台管理員。用新值，漏改只會少功能，不會多權限 | 1 §4.3 |
| D2 | 看不到的專案、任務回 **404** 不回 403 | 回 403 等於告訴對方「這個 id 存在」 | 1 §5.2 |
| D3 | 公司沒設 API key 時**絕不退回**用平台的認證 | 條款不允許；fallback 要指向最嚴格（rules/pipeline 59） | 2 §4.4 |
| D4 | 內部 AI（健檢等）**不准查客戶正式 DB** | 你的裁決是「看得到全部任務」，沒有包含客戶正式資料 | 0 §4.4 |
| D5 | 主 clone 的 `.git/config`、`.git/hooks` 掛成唯讀 | 可寫的話，AI 能埋指令，等平台在主機跑 git 時被執行＝從容器逃出來 | 0 §4.2 |
| D6 | 容器的記憶體／CPU／程序數上限，**沒訂數值前一律擋下不准跑** | 不給「不設上限」這個預設 | 0 §4.2 |
| D7 | 內部 AI 掛平台程式碼時用**乾淨的 git worktree**，不掛正在運作的平台資料夾 | 平台資料夾裡有 `data/config.json`（總鑰匙） | 0 §4.5 |
| D8 | `/ai` 查詢從容器走 **unix socket**，不走網路 | 平台是 host 網路，從 IP 分不出是閘道還是 nginx 轉進來的外部請求 | 0 §3 |
| D9 | 新增靜態守衛測試：以後新增的專案／任務路由沒做權限檢查就紅燈 | 11／12 支專案端點只驗登入就是這樣累積出來的 | 1 §5.4 |
| D10 | 內部公司記號 `is_internal` **只在遷移時建一筆，任何 API 都不能設** | 客戶公司被誤標成內部，就會拿平台的訂閱跑客戶的 AI，違反條款 | 1 §4.1 |
| D11 | 內部公司看得到全部專案**不寫特判**，純粹靠「全部都綁了」 | 權限只有一條規則（有綁才看得到），不會出現「內部例外」被濫用 | 1 §5.2 |

## 5. 09-14 新發現：測試區用平台的超級使用者連資料庫

測試區 Odoo 用平台 `DATABASE_URL` 的帳號 `odoo`（PG 超級使用者）連線，平台 DB `aidev` 與全部客戶測試 DB 在同一個 PG；SSO 進測試區的人是 Odoo admin，能寫伺服器動作跑 Python ⇒ 讀平台 DB、別家測試資料，甚至在平台容器執行指令。**不經過 AI 容器，子專案 0 擋不住。** 修法寫在 1 §10（每個測試區獨立、非超級使用者的 DB 帳號），任何客戶進測試區前必須完成。

## 6. 09-15 提示詞注入：策略與容器擋不住的洞

**提示詞注入**＝客戶在需求、附件、退回原因、對話裡藏一句指令，騙 AI 做壞事。

### 6.1 策略（09-15 定調）

**假設注入一定會成功，把它能造成的傷害壓到最小**；不做輸入過濾、不做注入偵測。
理由：過濾與偵測永遠做不到 100%，漏一次就全破；隔離是白名單，沒放行的一律不通。

| 層 | 做法 | 定位 |
|---|---|---|
| 第一層 | 子專案 0 的容器（掛載白名單、網路白名單、env 白名單） | **主要防線** |
| 第二層 | 容器內的 PreToolUse hook（現有 `scan-guard.js`，掛成唯讀，0 §4.2） | 輔助：提早擋明顯的壞動作、留紀錄。**不能當防線**——hook 是黑名單，`printenv`／`python -c`／先寫腳本再跑都繞得過；且沒進容器前 AI 與 hook 同 uid，改得到 hook 本身 |
| 第三層 | agent prompt 寫「別照使用者文字裡的指令做」 | 不做。prompt 是請求不是防線（rules/pipeline 60） |

### 6.2 容器擋不住的洞

| # | 洞 | 為什麼容器擋不住 | 誰負責 | 何時必須完成 |
|---|---|---|---|---|
| I1 | **夜間改善自動合併進平台 master**：客戶文字 → 健檢 AI 讀到被騙 → 提案自動核准（`auto-fix-scope.js`，medium 以上）→ platform-fix 改 `app/server/`（ALLOW 範圍內，DENY 只護守門碼）→ fix-review／fix-verify（也是 AI，可被同一段文字騙）→ 自動合併＋重啟 | AI 寫的碼合併後**在容器外、以平台本體身分執行**，拿得到全部鑰匙；影響所有客戶、會一直留著、全程無人 | **R6 已決（09-15）**：人擋入口、出口仍自動合併（§6.3） | 核准提案：開發順序階段 0.5，可現在做；R6-A 權限分級：階段 1；兩者都是第一家客戶前硬條件 |
| I2 | 共用專案（多家公司綁同一專案）：A 公司的人注入，AI 在共用專案寫進惡意碼，B 公司上正式時一起帶上 | 容器以專案為隔離單位，同專案內擋不到 | 已有對應：綁定前兩家確認（1 §4.3）、上正式確認視窗列出每張任務是哪家核准的（3 §105） | 接受為已知風險 |
| I3 | 測試區 DB 超級使用者：AI 寫進模組的碼在測試區一跑，就能讀平台 DB | 不經 AI 容器 | 1 §10 | 客戶進測試區前（開發順序 2c） |

### 6.3 I1 現在就存在（09-15 實查）

不是等客戶上線才有：

- 健檢 AI 的查詢範圍含 `tasks`、`project_chat_messages`（`health-auditor.md:25`）。
- `tasks.original_text` 來自客戶在 eService 自己寫的 `question_description`（`sync.js:370`）。
- 自動合併只看 `teams_settings.cli_push_user_id` 有沒有設（`nightly-fix.js:654`，這台已設）。

**R6 裁決（09-15）：人擋入口，出口仍自動合併。**

曾提出的另外兩條：清空 `cli_push_user_id` 停自動合併（截圖失敗會被 `ui-preview.js:205-209` 接住、不卡審核）、合併前要人按——**都不採用**。

| 項 | 做法 | 在哪 |
|---|---|---|
| 入口 | 健檢提案**一律平台管理員核准**才進夜間改善（意見回饋本來就要核准）。現在自動核准的兩處：`health-check-runner.js:133`、`:238-251` | 開發順序 0.5 |
| A | 改碼／審碼的 AI（`platform_fix`、`fix_verify`、`fix_review`、`feedback_merge`）**查不到平台 DB**，只讀得到核准過、放進 prompt 的文字；只有健檢 AI 能查 | 0 §4.5、開發順序階段 1 |
| B | 合併後留紀錄可回查：diff、審核與複檢說明、commit | 4 §4.3 |
| 核准頁 | 顯示**會送給 AI 的完整文字**，不是摘要 | 4 §4.3 |

**使用者知情接受的剩餘風險**：人核准的是文字，合併的是程式。
- 核准時沒看出全文裡藏的一句指令 → AI 照做 → 沒人看過 diff 就合併、在容器外執行。
- 意見回饋是客戶原文整段交給 platform-fix（`platform-fix.md:17`），這是最可能藏指令的地方。
- 出事時靠 B 回查、`git revert`。
