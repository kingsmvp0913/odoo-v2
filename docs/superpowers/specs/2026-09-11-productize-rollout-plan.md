| 做法 | 說明 |
|---|---|
| 功能開關可以**只對某家公司打開** | 開關除了全域開／關，還要能指定公司 id；測試時只開給「測試公司」 |
| 固定一家**測試公司**＋兩個測試帳號（公司管理員、一般使用者） | 階段 2a 建好後一直留著，之後每塊都拿它驗 |
| 測試公司只綁**測試專案** | 不綁任何真客戶專案；部署目標只用測試機，絕不指向真客戶正式機 |
| 攻擊實測腳本在正式平台跑 | 腳本是自己寫的，沒關好的結果是「測試不過」，不是真的外洩；但跑之前確認是對測試專案 |
| 重啟排時段 | 開發中重啟次數會變多，照 §2.3 先看在飛任務與測試區 |

**代價**：測試資料跟真資料在同一個 DB；staging 能擋的「改壞了整個平台起不來」擋不住，只能靠合併前全跑測試＋重啟排在沒人用的時段。

### 2.1-舊 另開 staging 平台的撞車點（R3 決定不開，保留供日後參考）

| 撞車點 | 為什麼會撞 | 怎麼避開 |
|---|---|---|
| 測試區容器名 | `odoo-test-<資料夾名>`，**沒有實例前綴**（`docker-env.js:77-80`）；建環境第一步就砍同名容器 | staging 的專案資料夾名一律 `stg-` 開頭；不複製正式 DB |

| 平台埠、內建 PG 埠 | 都是 host 網路；正式 `PORT`＝8771、`PGPORT_APP`＝8772（`docker/entrypoint.sh:11`） | staging 用另一組，開之前 `ss -ltn` 確認沒被佔 |

| nginx 設定 | 設了 `NGINX_*` 就會寫共用 nginx 的 conf（曾因此清空真設定，記憶 tests-wipe-real-nginx-conf） | staging **不設**任何 `NGINX_*`、`ENV_EXTERNAL_URL_TEMPLATE` |
| 客戶憑證 | 正式 DB 裡有客戶正式機 SSH、DB 連線、自動部署目標 | staging **用全新 DB**，不放任何真客戶連線 |
| 排程 | 夜間健檢、夜間改善、同步、測試區夜間關機都在 cron | staging 的排程全部關掉，要測哪個手動觸發 |
| Claude 用量 | staging 的 AI 若用同一組訂閱 token，會吃掉正式 pipeline 的額度（用量閘門是全域的，rules/infra 134） | staging 測試量控制小，重的測試排在下班時段 |
| compose | `docker-compose.yml` 寫死 `container_name: odoo-v2` | staging 另一份 compose 檔、另一個 project name、另一組 volume |

### 2.2 夜間改善會在開發期間自己改 master＋重啟（R1 已決：不暫停）

- `teams_settings.cli_push_user_id` 已設 ⇒ 夜間改善**自動合併進 master 並 `docker restart`**（`finding-fix.js:583-596`）。
- 夜間健檢 **22:00** 開始（`cron.js:121`），跑完才接著改善、合併、重啟。
- **使用者裁決 09-11：不暫停**（「我基本上都會是早上做」）。代價與對應：

| 會發生的事 | 對應 |
|---|---|
| master 半夜被改，開發分支隔天可能衝突（第 0 塊要改的 `claude-runner.js` 這類檔，正是健檢常修的地方） | 每天早上開工第一件事：把 master 併進開發分支、重量測試基線（§3 第 2 步） |
| 夜間合併遇到主 clone 有別人的暫存變更會拒絕合併 | 開發一律在獨立 worktree，主 clone 不留東西 |
| staging 一開，夜間重啟會認不出自己 | R2 已生效（09-14）；R3 決定不開 staging，這條目前不會發生 |

### 2.3 正式平台每次重啟的代價

- 在飛的 AI 被砍，任務卡在執行中（`runner.js:574`）。
- 測試區資料庫住在平台容器裡；重啟後測試區 bus 約 50 秒自癒，但 **Odoo cron 執行緒永久死掉，要重開那個測試區**（記憶 testenv-disconnect-from-platform-restart）。
- 重啟前先看：`/api/pipeline/inflight` 有沒有任務在跑、有幾個測試區在跑（09-11 實查只有 1 個）。

### 2.4 這台主機不是只有平台

20 核、187 GB 記憶體（可用約 140 GB）、磁碟剩 596 GB；**同時跑著約 110 個容器，其中很多是其他服務**。AI 容器與 staging 都要設資源上限，避免擠到別人。

## 3. 開發方式（每一塊都一樣）

1. 開自己的 git worktree 與分支，不共用 checkout（rules/always.md 5）
2. **每天早上**先把 master 併進開發分支（夜間改善可能改過），再全跑一次測試記下基線：`cd app && npm run test:quiet`（rules/always.md 1、2）
3. 合併進 master（開關關）→ 重啟 → 只對測試公司打開，在正式平台跑通（§2.1）
4. commit 只挑自己的檔（rules/always.md 4；平行 session 時用私有 `GIT_INDEX_FILE`，記憶 shared-index-race-on-commit）
5. 合併進 master，功能開關保持關
6. 攢一批，挑時段跑 `upgrade.sh` 重啟正式平台 → 重開正在跑的測試區
7. 在正式平台打開開關，先開小範圍，觀察後再全開
