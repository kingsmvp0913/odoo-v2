## 3. 現況事實（2026-09-11 實查）

### 3.1 夜間改善會自動上線

- 健檢提案經 `nightly-fix.js:144`（`inAutoFixScope`）**自動入選，不經人工**；意見回饋要 admin 核准。
- `teams_settings.cli_push_user_id` 已設 ⇒ `adoptFix → applyFix` 自動合併進平台 master。
- 合併後直接 `docker restart` 平台容器（`finding-fix.js:483-597`）。

### 3.2 平台重啟會影響客戶

- 測試區的資料庫住在平台容器裡（8772；`ss` 實查監聽 `127.0.0.1` 與 `10.0.0.1`）。
- 記憶 testenv-disconnect-from-platform-restart：平台重啟 → 測試區 bus 停約 50 秒可自癒，但 **Odoo 的 cron 執行緒會永久死掉，要整個 Odoo 重開**。
- 在飛的 AI 會被砍（`runner.js:574`；子專案 0 之後變成容器殘留，需啟動時清掉）。

### 3.3 平台資料庫沒有備份

- `pg_dump` 在 `docker/`、`scripts/`、`cron.js`、`upgrade.sh`、`DEPLOY.md` 都找不到。
- 資料在 docker volume `odoo-v2_pgdata`。
- rules/infra 121：搬 DB 必須連 `data/config.json` 的 `APP_SECRET` 一起搬，否則所有 `*_enc` 欄位（SSH 密碼、PAT、未來的客戶 API key）全部報廢。
- 有客戶之後，**所有客戶的任務、規格、對話、連線設定都在這個資料庫裡**。

### 3.4 容量

- 測試區埠池：`PROJECT_PORT_MIN`／`MAX` ＝ 21000–21099（`data/config.json`）。
- rules/infra 123 記錄 NAT 只轉發 21000–21012——這條可能已因子網域模式過時（記憶 external-access-decision），**要重新量**，不能直接引用。
- 目前 17 個專案、16 個測試區、執行中 1 個；平台是單一實例（記憶 multi-instance-shared-ai-dev）。

### 3.5 其他

- 刪專案逐表刪 `tasks` 系列與 `projects`（`project-routes.js:551` 起）；其餘表靠 CASCADE／SET NULL，沒有一份完整的「客戶離開要清哪些」清單。
- pipeline agent 的 `console.error` 不進 docker logs（記憶 pipeline-errors-not-in-docker-log）。
- 健檢的綠燈有虛胖問題（記憶 health-check-green-is-hollow）。
- 共用 nginx 的 443 沒有 `default_server`，conf 少一塊時測試區網域會拿到別的站的憑證（記憶 nginx-443-default-server-floats；當時使用者裁決不修）。
- 自助註冊存在（`auth.js:101`）。
- 通知管道：`notify.js` 可註冊 channel，已有 Teams webhook（`notify-webhook.js`）。

## 4. 設計

### 4.1 開通流程

平台管理員照順序做，新增一個「公司開通」頁顯示每一步有沒有完成：

1. 建公司：名稱、使用期間、啟用
2. 建公司管理員帳號
3. 建專案（自動綁內部公司）並綁到客戶公司，決定勾不勾「可上正式」
4. 綁公司 GIT（子專案 1 §6，會驗每個 repo 可存取）
5. 加 repo、DB 連線、正式機部署目標（沿用現有頁面）
6. 建測試區
7. 客戶管理員登入、填 API key（子專案 2），驗證通過
8. 用一張小任務走完整條流程，確認通了才交給客戶

### 4.2 訂閱

- 資料：`companies.is_active`、`active_from`、`active_until`（子專案 1 §4.1）。
- 擋的地方：子專案 1 §7 的檢查點。
- 到期前通知客戶管理員與平台管理員（天數見 §6）。
- 第一版**不串金流**：平台管理員收到款項後手動延長 `active_until`（見 §6）。

### 4.3 平台更版機制

**目的**：平台的改動不再「合併就立刻重啟」，而是累積、測過、挑時間一起上。

| 項目 | 現在 | 改成 |
|---|---|---|
| 夜間改善產出 | 自動合併 master＋重啟 | 只產出「已通過審核的修正分支」，停在待更版清單 |
| 健檢提案 | 自動入選 | 維持自動入選改碼，但同樣停在待更版清單 |
| 合併進 master | 自動 | 平台管理員在更版頁一次合併這一批 |
| 測試 | 每條修正各自跑 | 合併這一批之後，**整批再跑一次全套測試**（`npm run test:quiet`），紅了整批不上 |
| 重啟 | 合併後立刻 | 平台管理員選的維護時段 |
| 重啟後 | — | 自動重開所有執行中的測試區 Odoo（因為 cron 執行緒會死，§3.2） |
| 通知客戶 | — | 維護前在畫面上方掛公告 |

實作上最小的改法：`applyFix` 拆成「合併」與「重啟」兩段，合併也改成只在更版頁觸發。

**⚠ 09-15 R6 改寫了上表的兩列**（使用者裁決，總覽 §6.3）：

| 項目 | 改成（覆蓋上表） |
|---|---|
| 健檢提案 | **一律要平台管理員核准**才進夜間改善（跟意見回饋一樣），不再自動入選 |
| 合併進 master | **維持自動合併**，不經更版頁 |

重啟時段（O6 每週六日）、自動重開測試區、維護公告不受影響，照上表。
⇒ `applyFix` 仍要拆成「合併」與「重啟」兩段：合併自動做，重啟等維護時段。
⇒ 「合併後整批再跑全套測試」改成：維護時段重啟前，對 master 跑一次全套測試，紅了不重啟、通知平台管理員。

**這一塊同時是提示詞注入的防線（總覽 §6.2 I1）**：人擋在入口（核准提案／意見），出口（合併）不擋。所以：

- 核准頁要顯示**會送給 AI 的完整文字**，不是摘要——藏起來的指令只會出現在全文裡。
- 改碼的 AI 只讀得到核准過的文字（0 §4.5，R6-A）。
- 合併後留紀錄可回查（R6-B）：`finding_fixes` 已存 `diff`、`review_notes`、`verify_notes`、`commit_sha`，管理頁 `GET /api/admin/health-check/findings/:id/fix` 讀得到（`admin-routes.js:734-744`，只回最新一筆）；**計畫階段確認意見回饋來源的修正也看得到、且看得到歷史每一筆**。
- fix-review、fix-verify 仍保留，但它們是 AI，可能被同一段文字騙，**不算人工閘**。
維護時段、頻率見 §6。

### 4.4 平台資料庫備份（可以最先做）

- 每天 `pg_dump` 平台 DB（`aidev`，埠 8772；09-15 更正，原寫 `claude` 是錯的）。
- **09-15 實作**：平台 cron 臺灣時間每日 04:00（`lib/platform-backup.js`），`data/backups/platform-db-YYYYMMDD.dump`，留 14 天；失敗走 webhook／Teams（這台兩者都沒設），所以排程頁顯示「最近一次成功」與超過一天的警告。首次還原演練 09-15 通過（51 表、筆數一致、8 個加密欄位解得開、錯金鑰解不開）。每月演練尚未自動化。
- **`APP_SECRET` 另外保存**：沒有它，備份裡的加密欄位全部解不開（rules/infra 121）。備份檔與 `APP_SECRET` 放不同位置。
- 保留天數、異地位置見 §6。
- **每月做一次還原演練**：還原到一個空的測試資料庫，確認能開、加密欄位解得開。沒演練過的備份不算有備份。
- 備份失敗要通知平台管理員（§4.6）。

### 4.5 容量

- 上線前實測：這台機器能同時跑幾個 AI 容器＋幾個測試區（CPU、記憶體、磁碟）。
- 重新確認測試區對外埠與 NAT 範圍（§3.4），不沿用 rules/infra 123 的舊數字。
- 超過就排隊：沿用現有派工併發上限（rules/pipeline 64 的即時核對）。每家公司要不要有自己的上限，見 §6。

### 4.6 監控與告警

最小版，全部走既有 `notify` channel 通知平台管理員：

| 事件 | 來源 |
|---|---|
| AI 容器啟動失敗、docker／閘道不可用 | 子專案 0 |
| 閘道拒絕連線次數異常 | 子專案 0 的閘道 log |
| 公司 API key 失敗 | 子專案 2 |
| 正式部署失敗 | 子專案 3 |
| 平台 DB 備份失敗 | §4.4 |
| 公司即將到期 | §4.2 |

### 4.7 客戶離開

1. 停用公司（`is_active=false`）→ 客戶立刻無法登入、AI 不再跑
2. 保留期過後刪除：該公司全部專案（沿用刪專案流程）、測試區、repo clone、`data/agent-home/project-*`、wiki、embedding、對話與附件
3. `token_usage` 保留但去識別（改成公司 id，不留人名），供帳務對帳

計畫階段要**逐表**列出完整清單（§3.5：現在沒有這份清單），不能只沿用刪專案那段。
保留期、要不要先給客戶匯出資料，見 §6。

### 4.8 條款與責任（不是程式，上線前一定要有）

服務條款至少要涵蓋：

- 客戶自己按上正式造成的損害，責任歸屬
- 上正式前的資料庫備份政策（依子專案 3 P4 的結論寫）
- AI 產出程式碼的責任範圍
- AI 用量費用由客戶與 Anthropic 直接結算（子專案 2）
- 資料保留與刪除（§4.7）

另外：產品名稱、logo 不能含 Claude Code／Anthropic 字樣（子專案 2 §3.1）。

### 4.9 客戶建議怎麼變成平台改動

客戶「提意見」→ 平台管理員核准 → 夜間改善改碼、審核 → 進待更版清單 → 更版（§4.3）。
現行流程已經是這樣，只差最後一段不自動上線。

## 5. 測試

- 更版：夜間改善跑完後 master **沒有**新 commit、平台**沒有**重啟；更版頁合併後全套測試紅 → 整批不合併。
- 重啟後自動重開測試區 Odoo：用一個執行中的測試區驗證 cron 有恢復。
- 備份：還原演練腳本本身就是測試（還原 → 解一個 `*_enc` 欄位成功）。
- 訂閱到期：`active_until` 設成過去時間 → 子專案 1 的檢查點全部生效。
- 客戶離開：刪除後，用該公司的 id 對每張表查，全部 0 筆（去識別的 `token_usage` 除外）。
