## 1. 目標與非目標

### 目標

客戶自己走完整條路，**一般情況不需要平台人員介入**（合併衝突例外，見 §8 P1）：
提需求 → 回答澄清問題 → 確認規格 → 到測試區驗收（核准或退回）→ 上正式。

### 非目標

- 上正式前的資料庫備份（09-14 裁決不備份，§8 P4）
- 平台自己的更版（子專案 4）
- 流程本身的關卡設計（沿用現行 pipeline，不增減關卡）

## 3. 現況事實（2026-09-11 實查）

### 3.1 人工關卡（`app/public/js/pipeline-spec.js`）

| 關卡 | 狀態 | 端點 |
|---|---|---|
| 需補資料 | cs 閘門 | `POST /api/tasks/:id/cs-data-submit` |
| 等待確認回覆 | cs 閘門 | `cs-confirm`、`cs-followup` |
| 等待確認 | 分析後問問題 | `POST /api/tasks/:id/answer`、`clarify-ask` |
| 等待規格確認 | `spec_review` | `spec-approve`、`spec-revise` |
| 待你裁決 | `clarify_pending` | `answer`、`clarify-ask` |
| 失敗待確認 | `stopped` | `resolve-blocker`（填修正指示） |
| 合併衝突 | `merge_conflict` | `resolve-conflicts`、`mark-conflict-resolved`、`merge-clarify` |
| 等待審核 | `review_pending` | `approve`、`reject` |
| 🚀 上正式 | 專案層、整批 | `POST /api/projects/:id/release` |

- 任務層端點都經過 `loadTaskForActor`（本人或 admin）。
- `mark-conflict-resolved` 是「人工手解」：需要有人真的去改衝突檔（`git.js:558-559` 註解）。

### 3.2 核准（approve）

- 按下當下就驗 GIT 憑證（`pipeline-routes.js:57-62`）；push 回 ai-dev 歸屬到按的人（記進 `approved_by`）。

### 3.3 上正式（`project-routes.js:925-1030`）

- 合併 ai-dev → main：用**按的人本人**的 PAT，沒設就擋（930-936）。
- 部署正式機：要同時滿足 `auto_deploy_enabled`、有啟用的 prod 部署目標、**`isAdminUser`**（997）、`confirmDeploy === true`（1000）。
- 整批：`approved_at IS NOT NULL AND merged_to_main_at IS NULL` 的任務一起上（969-975）。
- 部署失敗回滾**只還原檔案，資料庫改動留在原地**（`deploy-run.js:187`，09-08 裁決）。
- 部署結果已經會寫進任務時間軸（記憶 deploy-fetch-missing-pat，`09a858f4`）。

### 3.4 給人看的文字

- 「給人看的文字有讀者、有出口，不再與工程訊息混流」已進 master（`735c21c5`，設計見 `2026-08-31-plain-output-design.md`）。
- 當時實測：規格書 `summary` 中位 189 字、13% 超過 400 字；QA 退回與審核分診的訊息術語最多。

### 3.5 測試區

- 客戶驗收要進測試區：SSO 端點 `env-routes.js:102`，閒置時會自動把環境拉起來。
- 進去時會依平台使用者 JIT 建 Odoo 帳號（記憶 sso-jit-create-hr-attendance-crash）。

## 4. 設計

### 4.1 誰能按哪個關卡

| 關卡 | 客戶一般人 | 客戶管理員 | 平台管理員 |
|---|---|---|---|
| 需補資料／等待確認回覆 | 自己的任務 ✓ | 自己公司成員的任務 ✓ | ✓ |
| 等待確認／待你裁決（回答問題） | 自己的任務 ✓ | 自己公司成員的任務 ✓ | ✓ |
| 等待規格確認 | 自己的任務 ✓ | 自己公司成員的任務 ✓ | ✓ |
| 失敗待確認 | 自己的任務 ✓（§4.5） | 自己公司成員的任務 ✓ | ✓ |
| 合併衝突 | ✗ | ✗；由平台處理 | ✓ |
| 等待審核（核准／退回） | 自己的任務 ✓ | 自己公司成員的任務 ✓ | ✓ |
| 🚀 上正式 | ✗ | 自己公司綁定有勾「可上正式」的專案 ✓ | ✓ |

任務層的規則全部落在 `loadTaskForActor`（子專案 1 §5.2），這裡不另開檢查。

### 4.2 核准

- 憑證改走子專案 1 §6 的「個人 → 公司」退回 ⇒ 沒設個人 GIT 的客戶也能核准。
- 時間軸寫明這次是用誰的 GIT 身分推的。

### 4.3 上正式

**權限**：`canReleaseProject(actor, projectId)`（定義在子專案 1 §5.2）＝平台管理員，或公司管理員且自己公司對該專案的綁定 `can_release=true`。
內部公司的綁定一律不勾（09-14 裁決）⇒ 客戶專案只有該客戶的公司管理員或平台管理員能按。
共用專案（兩家公司綁同一個專案）時，建議只勾一家；按下去會連另一家已核准的任務一起上線，確認視窗要列出每張任務是哪家公司的人核准的。

| 步驟 | 現在 | 改成 |
|---|---|---|
| 誰能按 | 任何登入的人都能合併 main；只有 admin 能部署 | 只有 `canReleaseProject` 為真的人 |
| 合併 main 的憑證 | 本人 PAT，沒設就擋 | 個人 → 公司退回 |
| 部署正式的權限檢查 | `isAdminUser`（997） | `canReleaseProject` |
| `confirmDeploy` | 必須 | 維持必須 |
| `auto_deploy_enabled` 開關 | 平台管理員（`project-routes.js:499` 已掛 `requireAdmin`） | 維持平台管理員（屬於開通） |

**按下前的確認視窗必須寫清楚**：
- 這次會一起上線的**每一張任務**：標題、提出者、核准時間（現有 `release-modal.js` 顯示了哪些，計畫階段確認後補齊）
- 「上正式前**不備份資料庫**；程式檔案失敗會自動還原，**資料庫的改動不會還原**」（§8 P4）

### 4.4 規格給客戶看得懂

- 「等待規格確認」預設**只顯示白話摘要**（`analysis.yaml` 的 `summary`＋驗收條件清單），YAML 原文收合起來，只有平台人員展開得到。
- 客戶可以用問的：`spec-revise`／spec-review agent 本來就支援「純提問」與「明確修改」兩種（記憶與 agent 說明）。
- 摘要長度：沿用 `735c21c5` 已做的出口規則；計畫階段抽 20 份現有規格，確認客戶版看起來合格再上。

### 4.5 失敗待確認

- 客戶看到的是**白話的原因**，不是 `blocker_content` 原文（原文收合，只有平台人員展開得到）。
- 客戶能做的事：填修正指示（沿用 `resolve-blocker`）。
- 提供「請平台協助」按鈕（§8 P2 已決）。

### 4.6 測試區驗收

- SSO 端點改用 `loadProjectForActor`（子專案 1 §5.3）。
- 客戶進測試區時維持 Odoo admin 權限；前提是測試區已使用獨立、非超級使用者的 DB 帳號（§8 P3、子專案 1 §10）。

## 5. 錯誤處理

| 狀況 | 做法 |
|---|---|
| 上正式時合併 main 衝突或失敗 | 維持現行：不標記 `merged_to_main_at`；客戶管理員看到白話說明，並通知平台管理員（這種失敗客戶沒辦法自己處理） |
| 正式部署失敗 | 檔案自動還原（`deploy-run.js`）；時間軸寫白話；通知客戶管理員**與**平台管理員；明寫資料庫改動未還原 |
| 客戶沒有個人 GIT、公司也沒綁 | 按鈕當下就擋，訊息「公司尚未設定 GIT，請聯絡平台」 |
| 公司不可用 | 子專案 1 §5.1，所有按鈕 403 |

## 6. 測試

- **角色 × 關卡矩陣**（supertest＋pg-mem）：一般使用者不能上正式；沒綁該專案的公司管理員不能；有綁但沒勾 `can_release` 的不能；有勾的能；內部公司的公司管理員對客戶專案不能；平台管理員全部能。
- `canReleaseProject` 單元測試（含共用專案：兩家都綁、只勾一家）。
- 核准與上正式在「沒個人 GIT、有公司 GIT」時能成功，時間軸記錄來源是公司。
- 確認視窗的任務清單在「開窗後有人又核准一張」時，實際上線的清單以按下當下查的為準（rules/infra 153，現行已如此，補測試鎖住）。
- 前端人工實測：用客戶一般人、客戶管理員各走一次完整流程（需子專案 0～2 都已完成）。
