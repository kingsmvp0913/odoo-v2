2026-08-25 複審鴻久（project_id=3）四張已 `done` 的任務，**QA 全部放行、但三張有實質缺陷**。已建 189~192 四張修正單，規格關與人工審核關都由使用者授權我代審（規格關退回改過 191、189 各一輪）。**190/191/192 經 odoo shell 實測後放行、已 done；189 因實測發現缺陷退回重修**（做法見 [[odoo-test-env-shell-testing]]）。

## 原四張的缺陷

- **187「修正退料」根本沒修到病根**（最嚴重）。使用者回報「新增一列填負數退料會報錯」，走 `create()` 路徑：`idx_repair.py:8544` 先算退料並 write `adj_qty`，`8576` 才 `super().create()` 把退料行落庫；而 `idx_maintenance.py:6699` 的 `@api.constrains("adj_qty")` 靠「DB 裡已存在負量退料行」算 `pending_return` 放寬下限。行還沒落庫 → `pending_return=0` → 下限退回已領量。配合 `repair_material_calc.py:38` 的 `ret = max((repair_qty+po_qty) - new_adj, 0)`，**當 `po_qty=0` 時「ret>0」與「違反約束」是同一件事**，必然報錯。`write()` 路徑沒事是因為 `8836` 先落庫。原 commit 只加了兩個抑制重算的旗標，對這條約束毫無作用。（Odoo 17 `models.py:4476` 證實 `write()` 內同步呼叫 `_validate_fields`，constrains 當場觸發、不延後。）
- **183 設定列名稱對錯報表**。`maintenance_pick_ec` 名為「叫修領料單（電控）」，實際同時控制 `download_pre_repair_report` 的 C6 格；`pre_repair_report` 實際控制維修後報告的委外分支。預設全開時看不出來，一關開關就關到別張。
- **184 下載按鈕的暫存檔被列成「訊息附件」**。`idx_repair.py:7057`／`7281` 每按一次下載就 sudo 新建一筆 `res_model='idx.repair'`、無 `res_field` 的 xlsx 且從不清除，正好符合新的 chatter 判定條件，按幾次長幾列。
- **185 邏輯拆分做對了**（`brings_repair_and_purchase_bom` 的虛設件 continue 沒被動，兩旗標各掛各的分支），但業務結果不對——只勾「不領料」會讓 `pool_consumption=0`，請購公式失去庫存項 → 有現貨也開全額請購並自動推 SM。使用者裁決：**請購演算法完全不動，現貨不保留給不領料品項、但判斷請購時仍要看當下庫存**。

## 189~192 修正單的關鍵決策

- **191**：第一版規格要用 `ava_qty` 整條取代 `repair_qty`，會誤傷一般品項（需求10、已領6、庫存20 → 原本請購4、改後變0）。退回要求拆成分支，一般品項算式一字不動，並補「一般品項扣帳後缺口與改動前一致」的驗收條件。
- **189**：第一版只找到 `pre_repair_report` 一半的引用點，漏了 `idx_report.py:30-34` 的 `_ALIAS_REPORT_KEY_BY_TYPE`（三個鍵各多控制一種 idx.report 記錄品名）。退回要求名稱寫兩個用途。另外它自己發現 data 檔是 `noupdate=1`、直接改 XML 對既有環境無效，加了 migration 且不動 `use_alias`——這點我原本完全沒想到。
- **190**：規格自己查核心擋掉我原本的建議（寫自訂 `res_field` 會讓 `ir_attachment.check()` 去 `env[res_model]._fields[res_field]` 而 KeyError），改用 orphan attachment。已驗證下載不會壞：`/web/content` 對內部使用者走 `validate_access()`（`ir_attachment.py:741`）直接 `return self`，Odoo 17 的 ir.attachment 沒有 read-time `check`。

## 實測結果（2026-08-25，於 test_odoo17_hungjou，全程 rollback 零殘留）

- **192 對照組是整輪最有價值的一步**：同一組資料（adj=10, repair_qty=10, po=0）跑舊順序（不先建退料行就寫 adj_qty）→ 拿到一字不差的 `ValidationError: 叫修評估量（7.0）不能低於已領料或已請購量（10.0）`；跑新碼 → 通過、退料行 qty=-3、adj 10→7、正向領料明細保留。**根因與修法同時被證實**。讀碼推導再嚴謹也給不了這個。
- **191 三場景**：不領料+庫存100→請購0；不領料+庫存0→請購10；**一般品項+已領6+庫存100→請購4**（回歸驗證，分支若拆錯會變 0）。
- **190**：新碼的 orphan 暫存檔不被列入、chatter 附件正常列出、**舊碼留下的暫存檔仍會顯示**（既有垃圾列不會自動消失，已知）。
- **189 被實測打臉兩次**。第二次更隱蔽：補刪除邏輯的 commit **只改 migration 檔、沒升 `__manifest__.py` 版本**，而測試區上一輪已升到 `17.0.1.0.4` 並跑過該目錄——**Odoo 只在「已安裝版本 < manifest 版本」時執行 migration，同版本直接跳過**。結果 coding／QA／deploy 三關全綠，那 8 行刪除邏輯一次都沒被執行，資料一個字沒變。QA 審 diff（diff 是對的）、deploy 驗能否升級（能升級），**沒有任何一關會問「這段碼真的跑到了嗎」**。修法＝版本升 `.5` ＋ migration 目錄改名 `17.0.1.0.5`（測試區 `.4`、正式區 `.3` 都會執行到）。改完實測：版本 `.5`、14 列、孤兒消失、`use_alias` 12 開 2 關（兩個 `sm_*` 關）未被洗掉。**⚠ 改 migration 內容而不升版號＝該修改在既有環境永遠不生效。**
- **189 第一次被實測打臉**：diff／migration／data 檔逐行核對全部正確，但測試區實際是 **15 列**——多一筆 `idx_report_product_name`（183 那輪 QA 判定的死開關，`e65b789` 從 XML 刪掉了）。**`noupdate=1` 讓「刪除」也不生效**，規格只想到它會擋「更新」。全新安裝 14 列、既有環境 15 列且該列 note 為空，acceptance 直接不成立。已退回要求 migration 補刪。**這個缺陷讀碼百分之百看不到。**
