2026-09-10 複審鴻久（project_id=3）254（出貨標籤）／257（用料調降不自動請購）／259（報告檔名帶叫修單號），
三張都是單一 commit（`79b2b4e`／`8149f2e`／`785fca0`），逐項比對 `analysis_yaml` 後**沒有阻斷級缺陷**，
但**全程只讀碼、一次都沒實跑**（本機無 reportlab，未進測試容器）。

**最反直覺的一件事：`review_pending` 不代表碼還沒合併。** 三個 commit 實測 `git merge-base --is-ancestor`
對 `testing` 與 `ai-dev` **都是 YES**。所以「等人工核准」等的是流程結案，不是程式碼進版——
要開後續任務去刪／改前一張的碼時，**不必等核准**，分支基底已經有它了。我原本假設要等，是錯的。

## 257 的兩個規格外發現（都不是 QA 抓得到的）
1. **`need_f = min(need_f, dedicated_qty_map.get(bom.id, 0))` 順帶關掉一種既有行為。**
   這行加在 `_bind_safety_stock_purchase`，用意是不讓「已被庫存池覆蓋的缺口」在確認時改以安庫請購冒出來。
   推演過：一般品項無影響（扣帳後 need_f 本來就 ≤ dedicated）。但 `no_material_issue`（不領料）品項
   **mat_qty 被強制歸零、repair_qty 不會增加**，庫存足時 dedicated=0 而 need_f 仍 >0 ⇒ 原本會綁一筆
   「轉安庫請購」，改完之後不綁了。規格沒寫這件事。使用者未裁決是否要追。
2. **提示訊息的數字會誇大。** `_notify_qty_decrease_outcome` 抓的 pur 是該 mtc_bom 在**所有未確認維修單**上的
   dedicated 總量，不是這次調降造成的量 ⇒ 之前已有 3 個請購、這次調降 1 個，會寫成「已轉請購 3 個」。
   使用者判定「容易造成誤會」，**已開 task 260「移除用料數量調降後的提示訊息」**（描述已寫明要保留
   `qty_locked` 池覆蓋與 `need_f` 封頂兩段核心邏輯，只刪提示）。

驗過但沒問題的：`simple_notification` 這個 bus 通道在 Odoo 17 核心確實存在
（`data/odoo-core/17/addons/bus/static/src/simple_notification_service.js`，收 message/sticky/title/type）——
**要判斷自訂 bus 通知會不會靜默失效，就去 `data/odoo-core/<版本>/` 翻，不要用記憶猜**。
259 同理查了 `web/controllers/binary.py`：`/web/content` 確實吃 query 的 `filename` 且優先於 `filename_field`。

## 254 留給人眼看的一點
UMC8 品名換成 2 行時，「訂單單號」順移 `line_h`（12pt×1.2≈5.08mm），與固定在 y=59mm 的 VENDOR
手算差 3.9mm、**約重疊 0.3mm**。規格 acceptance 明說座標是建議值不逐 mm 比對、跑版另行回報，
所以不構成退回理由，但要挑一筆長品名實印確認。
