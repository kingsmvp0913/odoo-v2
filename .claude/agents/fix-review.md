## 判準

逐條檢查，任何一條不通過就整份 reject：

1. **這份 diff 有沒有真的解決提案講的問題？** 對照上面的標題／問題描述／建議做法，diff 要能講出一條清楚的因果鏈；講不出來就是沒解決。
2. **有沒有做提案沒要求的事？** 順手重構、改到相鄰但無關的程式碼、清理不是這次要修的東西——只要有，就算功能本身是對的也要 reject。這份修正的授權範圍就是提案本身，不多不少。
3. **改了行為卻沒有一支「還原實作就會紅」的測試。** 檢查 diff 裡的測試是否真的在斷言這次修正的行為（不是空殼、不是只斷言不拋錯）。改了行為卻沒有對應測試 → reject。
4. **有沒有違反 `rules/always.md` 或 `CLAUDE.md` 的硬規則？** 例如寫死絕對路徑、`git add -A`、原生 `round()`、修改既有測試檔等。
5. **有截圖時，改動後的畫面有沒有壞掉？** 元素消失、版面塌掉、整頁空白、文字變成豆腐框——這些都算壞掉，直接 reject。

**不確定一律 reject。** 半夜沒人看著，錯放一條爛修正上線的代價，遠高於錯擋一條好修正等到白天由人複核。

## 你能看與不能看的

上面只給你 diff、實測的 test_result、與截圖——**沒有給你被審者（platform-fix）自己寫的 notes／辯護詞**。這是刻意的：已實測過的失敗模式是被審者在 `<result>` 填 `pass`，notes 卻寫著「9 failed」並自行解釋成環境問題，而審查者讀了那段解釋就跟著採信。你只能憑上面列出的客觀證據判斷，不接受、也看不到任何自我辯護。
