# 發問守則

適用於會產出「要使用者回答的問題」的關卡。各關的題目載體不同（結構化物件或字串陣列），
下列三條與載體無關。

## Q1 先攤決策樹，再決定哪些要問

動筆列題目前，先攤開這次要做的**決策點**：每個「有兩種以上做法」的地方就是一個節點。
逐點自問一句話：

**不同答案會不會讓你這一關做出不同的決定？**（不同的規格／不同的路由／不同的分類）

- 會 → 這是阻斷性模糊點，**必須列成題目**。
- 不會 → **自己決定**，把決定寫進 `intro` 或摘要告知，不要問。

最常被漏掉的節點是邊界情況：沒資料時畫面顯示什麼、數量為 0、權限不足的人看到什麼、
既有的舊資料要不要一起處理。逐一走過。

**剪枝是硬要求**：不是把每個分支都列成題目，而是把每個分支都**走過一遍**，
只列出會改變決定的那些。使用者要答的題目每多一題，他整份放棄回答的機率就升高。

## Q2 查得到的事實不准問

題目只能問「非使用者不可」的事——他的意圖、他的業務規則、他要的取捨。

| 這是什麼 | 該怎麼辦 |
|---|---|
| 現在的碼怎麼寫、某欄位存不存在、某按鈕掛哪個群組 | **自己讀 code**，不准問 |
| 這模組有沒有這功能、之前的規格怎麼定的 | 查 wiki／既有 `analysis.yaml`，不准問 |
| 使用者要什麼、業務規則怎麼訂、兩種做法他選哪個 | **問** |

把該自己查的包裝成問題，使用者只會回「這不是你該知道的嗎」——一輪往返白花，信任也掉。

## Q3 每題附建議答案與猜錯的代價

不准丟白卷。要讓使用者是在**審查提案**，不是面對空白。每題含三件事：

1. **問題本身**：一句話，用他在畫面上看得到的名字。
2. **你的建議答案＋一句理由**：依既有寫法、依同類功能的慣例。
   - **唯一例外：純屬「他要什麼」的題目不附建議**（業務規則怎麼定、要不要這個功能、哪種呈現才是他想要的）。
     那是定義不是推導，你手上沒有依據，附了只是誘導他按你的預設。判準是「我這個建議說得出依據嗎」——
     說不出來就留空，不要為了每題都有而編一個。
3. **猜錯的代價**：照實選一種寫法——
   - 「這裡若選錯，之後隨時能改，不用重做」
   - 「這裡若選錯，要退回重寫規格與程式，請多看一眼」

有選項欄位的載體，建議標在選項文字裡；只有字串的載體，建議與代價接在問題句子後面。
**沒有代價說明，等於要求使用者對每題同等謹慎**——他會卡在最不重要的那題上。
