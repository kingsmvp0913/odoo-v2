# 題目撰寫契約

適用於任何要輸出 `clarification_channel.questions` 結構化題目的關卡。違反下列任一條，
會讓畫面編號錯亂、或強迫使用者回答不該由他回答的題目。

- 白話說明、背景、「這部分不用您決定」這類**不是問題的內容一律放 `intro`**，不得放進 `questions`。
- `questions` 每一筆是一個**獨立問題**的物件：`id`／`text`／`type`（`choice`｜`text`）／`required`，
  `choice` 另附 `options`（每項 `key`＋`label`）。
- **每題附 `impact`**：`costly`＝選錯要退回重寫規格與程式；`reversible`＝之後隨時能改。
  畫面會把 `costly` 渲染成一個小標記，讓使用者一眼看出哪幾題要多看一眼——**所以絕對不要再把這件事
  寫進 `text` 或 `recommended_why`**，寫了只會讓題目越來越長，標記已經講完了。判不出來就填 `reversible`。
- `text` 內**不得自帶「Q1：」「問題1：」之類的編號**——畫面會自己編號，自帶會變成雙重編號。
- `text` 內**不得寫「只有第 1 題選 A 才需要回答」**這類條件敘述——條件用
  `depends_on: { question: q1, equals: A }` 欄位表達。
- 能給選項的一律用 `type: choice` 並把選項放 `options`，不要把 (A)(B)(C) 寫進 `text` 讓使用者自己打字。
- **推導得出答案的題目要附 `recommended`**：`choice` 題填你建議的 option `key`，`text` 題填一句話；
  另附 `recommended_why` 一句話寫依據（你在 code 裡看到什麼、既有做法是什麼）。使用者要的是有依據的
  預選，不是一排等他自己權衡的選項。
  - **「使用者要什麼」這類題目一律不附**：業務規則怎麼定、要不要這個功能、哪種呈現才是他想要的——
    那是定義不是推導，你手上沒有依據，附了只是誘導他按你的預設。這種題目留空 `recommended`。
  - 判準是「我這個建議說得出依據嗎」。說不出來就是不該附，不要為了每題都有而編一個。
- **已經問過且得到答案的點，不得換個說法再問一次。**
