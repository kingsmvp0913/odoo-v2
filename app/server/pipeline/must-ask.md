# 這三種一律要問——但先確認你說不出有依據的預設

適用於任何會產出「要使用者回答的問題」的關卡。下列三種是走【發問守則】決策樹時**最容易被整個漏掉的
節點**，逐條走過一遍，不准跳過。

**走過之後，用同一個判準決定要不要列成題目——「你說得出有依據的預設答案嗎？」**
依據＝程式碼裡看得到的既有做法、同類功能的慣例、規格裡已定的規則。

- **說得出** → **自己決定**，把決定與那句依據寫進 `intro`（沒有 `intro` 的關就寫進回覆摘要）告知，
  **不要列成題目**。他看到後不同意，隨時能在後面的閘門推翻你——那比現在攔住他問一輪便宜。
- **說不出**（純屬「他要什麼」：業務規則怎麼定、要不要這個功能、哪種呈現才對）→ **一律要問**。
  這種硬填進規格＝你替他定了業務規則，錯了要整條線退回重做。

判準只有上面這一句。**不要拿「這題看起來明不明顯」「他大概會選哪個」當理由**——那是憑印象；
「我說得出依據嗎」才是當場檢查得了的。

- **同一句需求／同一個要求有兩種以上合理做法，而你必須挑一種**——把你要選的與你放棄的並排看一次。
  例：「加折扣欄位」「折扣欄位改成可編輯」→ 折扣是百分比還是金額？算稅前還是稅後？
- **他只描述了正常情況，實作／改規格卻得決定異常怎麼辦**——空值／零／負數／重複／超出範圍／
  已過帳的單據還能不能改／既有舊資料要不要一起處理。
- **這個改動會波及他沒提到的既有畫面或流程**——影響範圍你讀 code 看得到，他看不到。
  問法是「這裡會跟著變成 X，是你要的嗎」，**不是**「可以嗎」。
