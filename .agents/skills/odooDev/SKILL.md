# odooDev — Odoo 開發參考

**這份不是規則書。** 每次都要遵守的硬規則（`_inherit`／view 繼承／檔案命名／`idx_` 前綴／權限錨點 P0–P6／禁用原生 `round()`／原生 SQL 前後 flush｜invalidate）已經在你的系統提示詞裡，本頁**刻意不重抄**——抄第二份必然漂移，屆時兩份說法不同而沒有任何訊號。

本頁放的是「需要時才查」的參考：**怎麼查證**，以及**已經有人踩過、且有出處可複驗的陷阱**。

## 一、查證的優先序（別跳過第一順位）

1. **Odoo 核心原始碼** — 你的系統提示詞裡已經給了本專案對應版本的核心碼路徑。欄位型別、decorator、method 行為、原生 view 的 xpath 目標節點、selector／class 名，**一律以那份原始碼為準**。
2. **Context7**（`resolve-library-id` → `query-docs`）— 查官方文件與版本差異。
3. **你的記憶** — 最後順位。Odoo 各版本之間 API 差異大，記憶裡的寫法很可能是別的版本的。

判斷「這是 bug 還是原生行為」時，**只有第 1 順位算數**：拿得出核心碼的檔名與行號，才叫確認。

## 二、已驗證的核心行為陷阱

下列每條都附出處，可自行複驗；沒有出處的推測不要加進本頁。

### combo 商品：主行價格永遠是 0

`sale.order.line` 的 combo 主行價格恆為 0，價格分攤在各子行；把主行轉成 `line_section` 也是核心自己的行為，不是客製造成的。
（出處：核心 `addons/sale/models/sale_order_line.py`，搜 combo 相關的價格計算）
→ 因此「combo 訂單開票金額為 0」多半是**測試資料把價格塞在主行**，不是開票邏輯壞掉。

### `_create_invoices(grouped=False)` 仍會依客戶合併

`grouped=False` 不等於「一張訂單一張發票」。同一個客戶的多張訂單仍會被合併成一張發票。
→ 要測「不同稅別各自開票」這種情境，測試資料必須是**不同客戶**；用同一個客戶建兩張單，看到的合併是正確行為。

## 三、造測試資料的陷阱（這一類最會製造假 bug）

**用 RPC／ORM `create` 直接塞值，會繞過本來由 compute 決定的欄位**，於是造出現實中不可能出現的資料，然後你會在那份資料上「發現」一個不存在的 bug。實際發生過兩次，兩次都差點把正確行為報成缺陷。

動手前先問自己兩件事：

1. **這個欄位是誰算的？** 若它有 `compute`／`onchange`，就不該由你指定，要走會觸發計算的路徑。
2. **下游會不會把它們合併？** 出現「A 對、B 對、A+B 錯」時，第一個要懷疑的是下游合併（如上面的發票合併），而不是邏輯錯。

## 四、版本差異

不同專案的 Odoo 版本不同，**同一個 method 在 17／18／19 可能簽名不同或已移除**。寫之前先確認本專案版本（系統提示詞裡有），再用第 1 順位的核心碼複驗。跨版本升級時尤其不要沿用記憶中的寫法。
